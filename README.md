# Threads Clean Link

一鍵把 Threads 的分享連結和「複製連結」結果,都變成不帶追蹤參數的乾淨貼文網址。

## 兩大功能

### 右鍵還原分享短連結

Threads App 的「複製連結」會產生 `/share/XXXX` 這種短連結。不管這個連結出現在哪個網站——Threads 網頁版、其他社群平台、聊天室、論壇——只要在連結上按右鍵,選擇選單裡的「**複製乾淨的 Threads 貼文連結**」,就能一鍵把它換成乾淨的貼文網址,並自動複製到剪貼簿。

```
分享短連結  https://www.threads.com/share/AbCdEfGhI
還原結果    https://www.threads.com/@username/post/AbCd123EfGh
```

這個自動複製動作不限定要在 threads.com 分頁上才能用:你按右鍵、點選單的那個操作手勢,會臨時授權當下分頁執行一次剪貼簿寫入,所以不論你在哪個網站看到分享連結,都能直接右鍵拿到複製好的乾淨網址,不需要先切到 Threads 分頁(細節見下方〈權限清單〉)。

### 自動淨化網頁版「複製連結」結果(含短碼自動解析)

Threads 網頁版官方的「複製連結」按鈕,寫入剪貼簿的內容目前有兩種可能:一種是 `/share/XXXX` 短碼,一種是帶 `?xmt=...` 追蹤參數的完整貼文網址,取決於 Meta 當下的實作。Threads Clean Link 兩種都處理:攔到短碼,就自動解析成乾淨貼文網址;攔到帶參數的完整網址,就直接剪掉參數——對你來說都是無感完成,貼上就是乾淨網址,不需要額外操作。

背景:2026 年 7 月底的研究確認網頁版「複製連結」原本就是給完整網址,只有 App 端才會產生短碼;2026 年 8 月前後 Meta 把網頁版也改成寫入短碼,本擴充功能因此把短碼解析內建進複製流程,兩種格式都涵蓋。短碼解析設有 2.5 秒逾時,逾時或請求失敗都會讓內容原樣放行,不會卡住、也不會弄壞你原本的複製功能,只是這次沒能幫你濾掉追蹤資訊。

## 運作原理

### 分享短連結為什麼不能「直接算」出來?

`/share/XXXX` 是一次性代碼,會關聯到分享者帳號(類似 IG 連結的 `igsh`),對照表只存在 Meta 的伺服器裡,**沒有任何本地端的規則或正則式能把它還原成貼文網址**——這和「網址裡藏了一段編碼過的資訊」不同,短碼本身不含任何可解析的資訊,唯一辦法是實際問伺服器一次:「這個短碼實際指向哪裡?」

具體做法:對短連結發一次**不帶 cookie 的匿名 GET 請求**,讓瀏覽器自動跟隨轉址,取得轉址後的最終網址,再把 `?xmt=...` 之後的追蹤參數切掉,就是乾淨貼文網址。

### 淨化功能什麼時候要問伺服器、什麼時候不用?

網頁版「複製連結」按下去的當下,官方頁面寫入剪貼簿的內容分兩種情況:

- **帶追蹤參數的完整貼文網址**:官方程式碼已經準備好完整、正確的目標網址,只是多附加了 `?xmt=...` 之類的追蹤參數——這不需要問任何人,純粹是字串處理,零請求。
- **`/share/XXXX` 短碼**:和上一節的分享短連結是同一種東西,一樣不含真實目標的任何資訊,套用同樣的邏輯——必須向伺服器問一次。淨化功能攔到短碼時,會自動觸發和右鍵還原相同的一次匿名 GET,解析出乾淨網址後再寫入剪貼簿。

Threads Clean Link 在 Threads 頁面(threads.com / threads.net)裡安裝一層「濾網」,攔截頁面**自己**透過瀏覽器標準剪貼簿 API 寫入的內容,先判斷是短碼還是帶參數的完整網址,分別用上面兩種方式處理後再放行。這層濾網本身不直接連線任何伺服器;只有判斷出內容是短碼時,才會透過背景程式代為發出一次解析請求。它也只包住網站自己呼叫的剪貼簿寫入,不涉及讀取剪貼簿裡原本的內容。短碼解析設有 2.5 秒逾時,逾時或請求失敗一律原樣放行,不會卡住或弄壞複製功能。

## 權限清單

擴充功能宣告的權限,逐項列出實際用途,方便你自行對照 `manifest.json` 核對:

| 權限 | 用途 |
|---|---|
| `contextMenus` | 在分享短連結上加一個右鍵選單項目 |
| `scripting` | 注入目前分頁,執行一次 `navigator.clipboard.writeText`,把還原後的乾淨網址寫進剪貼簿 |
| `notifications` | 還原完成後跳通知,讓你知道已經複製成功 |
| `activeTab` | 只在你點右鍵選單的那個操作手勢當下,臨時授權那一個分頁;不是常駐權限,分頁一換或沒有互動就失效 |
| host permissions `https://*.threads.com/*`、`https://*.threads.net/*` | 讓背景 service worker 能對 Threads 網域發出匿名請求解析短碼、讓淨化濾網能在 Threads 頁面上運作 |

明確不包含:**不宣告 `<all_urls>`**(不會取得瀏覽其他網站內容的常駐權限),**不宣告 `clipboardRead`**(沒有讀取剪貼簿現有內容的能力,只能寫入)。

## 誠實隱私聲明(請務必讀完這段)

這個擴充功能標榜保護隱私,但誠實比行銷話術重要,以下是兩個功能的真實網路行為,一項不省略:

**右鍵還原功能「會」對外發送網路請求。** 使用右鍵選單還原分享短連結時,本擴充功能會在背景向 `threads.com` 發出一次**不帶 cookie 的匿名 GET 請求**(瀏覽器會自動跟隨其轉址),藉此取得短碼實際指向的乾淨網址。效果等同於「用無痕模式點了一次那個分享連結」——可能會讓原分享者的貼文開啟數 +1。這次請求不帶登入憑證與 cookie,因此不會以你的登入身分送出;但誠實地說,請求仍會讓 Meta 看到你的來源 IP 與瀏覽器特徵,這是任何一次網路連線都無法避免的——如果連 IP 層級的關聯都想避免,請搭配 VPN,或不要使用這個功能。另外,這個請求是由擴充功能發出的,可能帶有能讓 Meta 辨識「這是來自本擴充功能」的 Origin 標頭,但這個標頭本身仍不含你的身分資訊。這是短碼問題「必須向伺服器問一次」的技術本質決定的,沒有繞過的辦法,我們選擇把它老實寫在這裡,而不是含糊帶過。

**淨化功能不再保證零網路請求(2026 年 8 月更新)。** 這點請仔細看:自動淨化功能現在分兩種情況處理,網路行為不一樣。**當且僅當**網站寫入剪貼簿的內容是 `/share/XXXX` 短碼時,擴充功能才會自動觸發一次和右鍵還原功能完全相同的**不帶 cookie 匿名 GET**——這次是被動攔截後自動發出,不需要你做任何手勢,適用範圍與隱私影響請對照上一段的說明。如果攔到的是已經帶 `?xmt=...` 追蹤參數的完整貼文網址,則維持原本的做法:純文字處理、零網路請求。短碼解析若逾時(2.5 秒)或失敗,會讓內容原樣放行,不會卡住、也不會弄壞你的複製功能,只是這次沒能濾掉追蹤資訊。無論哪種情況,這層濾網都只檢查網站自己透過標準剪貼簿 API 寫入的內容,不符合 Threads 貼文網址或短碼格式的一律原樣放行,不儲存、不傳送、不留紀錄;其他網站上的複製行為,以及你在 Threads 頁面上手動 Ctrl+C / 選取複製的內容,完全不經過本擴充功能。另外要提醒:②的解析請求是緊接在你於已登入的 Threads 分頁按下「複製連結」的當下發出的——時間與貼文都對得上,對 Meta 而言 IP 層級的關聯性比右鍵還原(①)更高。在意這點的話,請改用①的右鍵方式處理,或搭配 VPN。

| 功能 | 網路請求 | 讀取剪貼簿 |
|---|---|---|
| 右鍵還原分享短連結 | 有,1 次不帶 cookie 的匿名 GET(瀏覽器會自動跟隨其轉址) | 否(只負責寫入還原結果) |
| 自動淨化複製連結 | 短碼:1 次不帶 cookie 的匿名 GET／參數剪除:零 | 否(只攔截網站自己的寫入,不讀取既有內容) |

**與 ClearURLs 這類純參數清理器的本質差異。** ClearURLs、Linkumori、CleanURL 這類工具標榜零網路請求,做法是拿到完整網址後,用規則庫剪掉已知的追蹤參數(例如 `utm_source`)——整個過程網址本身完整可見,純粹是文字處理,自然不需要連網。但 Threads 的 `/share/XXXX` 短碼**不是參數,是整條網址**,它不含真實目標的任何資訊,規則庫無法從中「剪」出貼文網址,必須先向伺服器兌換一次才有東西可以清理。這也是為什麼 Threads Clean Link 的兩個功能都可能觸發這次解析請求:不管是右鍵手動觸發,還是複製連結被動攔到,只要遇到的是短碼就必須問伺服器一次;只有拿到的內容已經是帶追蹤參數的完整網址時,才能維持零請求。

## 安裝

尚未上架 Chrome Web Store,目前請以「載入未封裝項目」方式安裝:

1. 取得原始碼,擇一即可:
   - 下載或 clone 整個 repo:
     ```
     git clone https://github.com/hunandy14/threads-clean-link.git
     ```
   - 或直接到 [Releases](https://github.com/hunandy14/threads-clean-link/releases) 頁面下載已打包好的 zip 並解壓縮——每次 main 分支的版本號更新,CI 都會自動打包發布,不想 clone 整個 repo 的話這個方式更快
2. Chrome 網址列輸入 `chrome://extensions`
3. 右上角打開「開發人員模式」
4. 點選「載入未封裝項目」,選擇剛才 clone 或解壓縮出來的資料夾
5. 完成。右鍵還原功能在任何網站的分頁上都能用;自動淨化功能只在 threads.com / threads.net 的頁面上運作

Chrome Web Store 上架(含註冊費、審查與隱私權說明)是後續規劃,屆時會在此更新連結。

## FAQ / 已知限制

**手機 App 分享出去的連結,會被這個擴充功能淨化嗎?**

不會。**自動淨化**功能是瀏覽器擴充功能,只在 Chrome 分頁載入 threads.com / threads.net 網頁版時運作,不是系統層級的剪貼簿監控工具;手機 App 的分享或複製連結,只要沒有經過你電腦上的 Threads 網頁分頁,淨化功能碰不到、也管不到。不過如果那個分享連結在某個網頁上被顯示成可以點擊的超連結(例如貼在聊天室、論壇),你仍然可以對著它按右鍵,用**右鍵還原**功能複製出乾淨網址——這個功能不限定要在 threads.com 分頁上才能用。

**Meta 改版會不會讓這個擴充功能失效?**

有可能,但風險集中且可控,已知會受影響的變動點都屬於「壞得明顯、修得容易」:

| 風險點 | 說明 | 修復成本 |
|---|---|---|
| 網域更換 | 已有前例:2024 年 threads.net → threads.com | 改一行網域比對規則 |
| share 路徑格式 | `/share/XXXX` 格式變動 | 改一行路徑比對規則 |
| 轉址行為 | 匿名請求不再回傳 302、改跳驗證頁 | 調整請求方式 |
| 貼文網址格式 | `@帳號/post/ID` 格式變動 | 小幅調整解析邏輯 |
| 複製連結寫入格式 | 網頁版在短碼與完整網址之間切換(已發生過一次:2026 年 8 月) | 兩種格式已都納入處理,如再變動則比照其他列調整 |

功能失效時通常會直接沒反應,而不是悄悄壞掉;修復也通常只需要改一兩行比對規則,不涉及架構重寫。

**為什麼不做成像 ClearURLs 那樣的通用型追蹤參數清理器?**

刻意把範圍維持小:這個擴充功能只做 Threads、只做這件事。通用型清理器已經有成熟方案,但它們都不處理「短碼問題」——這正是本專案存在的理由。
