# LINE 群組引導警示設計文件

本文件描述插件端「LINE 群組引導警示」的設計：使用者自己點進 Threads 貼文詳情頁時，就地判斷這一串貼文是不是「長篇投資心得＋末篇引導加 LINE」的招攬劇本，命中就把作者記進警示名單（**預設只存在這台裝置**；登入雲端同步後會跟著使用者的帳號同步，貼文文字片段仍留在本機），並在頁面上掛一枚標記。範圍限於插件端的偵測規則、本機儲存、訊息協議與介面行為。

## 1. 目的與範圍

投資招攬帳號的共通劇本是：正文經營人設、談投資獲利或職涯轉折，再在自回覆串的尾端留一個 LINE 提及，把人帶去私訊或群組。單看任何一半都可能是正常內容——交友貼文會留 LINE，讀書會也會揪人進群組——所以標記的判準是兩類訊號同時出現。目的是在使用者還沒加好友之前，把這個訊號擺到他眼前。

| 項目 | 設計 |
|---|---|
| 資料落點 | 警示名單與證據一律寫 `chrome.storage.local`，備援請求的節流表寫 `chrome.storage.session`（瀏覽器關閉即清）。名單**預設只存在這台裝置**；使用者登入雲端同步且總開關開啟時，才隨帳號同步到開發者自營後端（**貼文文字片段與當時開的頁面網址不上傳**，見 `docs/cloud-sync.md` D35–D40）。節流表、匯出／匯入檔一律不含名單，也不做社群回報或跨使用者共享 |
| 觸發時機 | 只有使用者自己開啟某篇貼文的**詳情頁**才掃描該頁；不遍歷河道全文、不枚舉串文、不背景輪詢、不預先抓取 |
| 掃描對象 | 該頁已經送到瀏覽器的內容（伺服器預載資料與頁面 DOM），不另外向 Threads 索取串文內容 |
| 權限 | 沿用既有的 threads.com／threads.net content script 與 `storage` 權限，`manifest.json` 的**權限陣列零變更**；manifest 另新增 `minimum_chrome_version: "103"`（備援請求用的 `AbortSignal.timeout()` 自 Chrome 103 起才有）與 `tcl-core.js`、`scam-guard.js` 兩支 ISOLATED content script 新檔 |
| 總開關 | 選項頁設定卡「LINE 群組引導警示」，**預設開啟**；關閉後不掃描、不標記、不寫入，也不發出任何請求 |
| 判定位置 | 全部在本機完成，不呼叫任何伺服器做判斷，不含遠端程式碼、不含遠端規則更新 |

河道（首頁時間軸）不掃全文——整頁都是別人的貼文片段，掃了只會製造誤判。河道只做一件事：拿貼文卡片上的帳號去查本機警示名單，已知作者才標記。

## 2. 偵測規則

招攬串的共通結構不是投資話術，而是**「LINE 提及 ＋ 把人拉進群組／要人加好友」**這組動作——軟性招攬串（長篇心得鋪陳、末篇只留一句「加 LINE：xxx，我把你拉進群組」）整串一個話術詞都不放。命中因此走三條路：

| 路徑 | 條件 |
|---|---|
| 連結型錨點 | 深連結本身就是「加好友／加群組」的入口，單獨成立 |
| 提及 ＋ 行動呼籲 | LINE 提及 ＋（群組詞 或 加入詞） |
| 錨點 ＋ 強話術詞 | 連結／帳號／片語三型錨點 ＋ 至少一個強話術詞（既有路徑，保留） |
| ID 跨帳號（v4，D46） | 這串抓到的 `lineId` 已在警示名單派生的 `lineIdIndex` 上，且索引指到的是**另一位**作者 |

話術詞不再是任何門檻的必要條件，只列入證據（見 2.3）。

第四條路徑不在 `detectScamPitch` 內部判定，而是 `scam-guard.js` 拿到 `detection.lineId` 之後另外查表（見 2.7、第 4 節）：索引查到的 `userId` 存在、本篇作者的 `userId` 也取得到、且**兩者不同**才算——索引指回本篇作者自己時不算（自己貼自己的 ID 是常態，算了的話名單上每個人的每一篇都會被自己的 ID 再標一次），作者主鍵取不到時也不算（比不出「是不是同一人」就不該據此判定）。索引只含 `state === 'active'` 的條目，使用者解除過的作者不會再把別人拖下水。這條路命中時 `signals` 補 `id-match`；`detectScamPitch` 本身未命中（`hit: false`）時不產生 `anchorMatch`／`snippet`，改由 `scam-guard.js` 以 `lineId` 在原文中的位置另行裁切（同一套 40／120 字視窗）。

規則的詞表與正則集中在 `tcl-core.js` 的 **`SCAM_RULES`** 物件，`detectScamPitch(text, rules)` 的第二參數可選、預設就是它：規則是資料、判定是邏輯，後續可改為由後端下發規則包而判定邏輯不動。

**目前規則版本：`SCAM_RULES.version = 4`。** v4 把「對方的 LINE ID」升成第一級證據：帳號型錨點的繫詞放寬（`賴號ID：`／`LINE 帳號 : `／全形空白）、新增暗號型行動呼籲（`傳「177」給我`／`留言【18】`／「暗號」一類的加入詞）、`detectScamPitch` 多回一個 `lineId`（命中時連帶把標亮位置改成 ID 本體），並由警示名單派生一張 `lineId → userId` 的反查表，讓同一個 ID 換一個帳號再招攬一次照樣認得出來（訊號類別因此補上 `account`／`phrase`／`id`／`id-match`）。

### 2.1 LINE 提及（mention）

| 類型 | 樣式 | 可走哪幾條路 |
|---|---|---|
| 連結型 | LINE 加好友／群組深連結（`line.me` 的 `ti/p`、`ti/g` 路徑，含帶 `R/` 的舊式變體 `line.me/R/ti/p/`、`line.me/R/ti/g/`；`ti/p` 路徑段容許前導 `~`——`line.me/ti/p/~帳號` 是 LINE 官方加好友深連結的寫法，字元類少了它就在 `~` 前斷開）、`lin.ee` 短網址、`linktr.ee` 聚合頁；`https://` 與 `www.` 都可省 | 三條都算，且可單獨成立 |
| 帳號型 | 「賴」「籟」「LINE」＋ 繫詞（`是`／`ID`／`帳號`／`號`／`號ID`／`號碼`，大小寫不拘、可省）＋ 半形／全形冒號（冒號前後容許空白，含全形空白 U+3000）＋ 至少 3 位帳號字元（上限取 LINE ID 官方的 20 字） | 提及、錨點 |
| 片語型 | 加好友祈使句：「加入我的」「加入我」「加入」「加我的」「加我」＋ 賴／籟／LINE，以及不必帶這些前綴的「加 LINE／加LINE」 | 提及、錨點 |
| 單字型 | `LINE` 單字，前後都不接英文字母 | 只走「提及 ＋ 行動呼籲」，且只認主動招攬詞 |

`line.me` 的其他路徑（官網首頁、分享頁）不算連結型錨點，那些不是引導私訊的入口。連結型省掉 `https://` 是因為招攬文常直接寫「lin.ee/xxx」，Threads 自己會渲染成連結；省掉之後改以前置的負向邊界擋住黏在別的網域後面的情形（見 2.4）。

### 2.2 行動呼籲：群組詞與加入詞

- **群組詞**：群組、社群、群裡、進群、拉進、拉你進、小群。
- **加入詞**：加入、加我、私訊我、暗號、通關密語、密語（後三者為 v4／D45 新增）。
- **主動招攬詞**（上兩張表的子集，描述「把你帶走」這個動作）：進群、拉進、拉你進、小群、加我、私訊我、暗號、通關密語、密語。

**暗號型行動呼籲的樣式**（v4／D45）：詞表認不出「傳「177」給我」「留言【18】」這種把代碼包在引號／括號裡的祈使句，另外用兩條樣式抓，命中任一條就與加入詞同一個待遇（錨點型提及與單字型提及都認）：

1. 代碼被引號或括號包住——「傳訊「63」」本身就成立，不必再接「給我」。
2. 裸代碼後面接「給我」——「傳 177 給我」。

代碼上限 8 位：再長就不是人記得住的暗號，而是識別碼或網址片段。代碼是必要條件——「傳訊息給我」「把檔案傳給我」沒有代碼，兩種形狀都踩不到，不算行動呼籲，也不算日常用語「給我」。

門檻**分兩層**：錨點型提及（連結／帳號／片語）已經帶著帳號或祈使句，吃完整的群組詞＋加入詞；**單字型提及只認主動招攬詞**。「群組」「社群」「加入」是名詞，公司公告、社區公告、讀書會、商家會員貼文本來就會跟 LINE 同框——「公司公告改用 LINE 群組發布」「LINE Pay 加入會員送點數」不該進警示名單。

兩類詞都**必須獨立於提及本體之外出現**。「加入我的 LINE」整段就是一個片語型提及，裡面的「加入」不得再充當加入詞——否則「加入LINE官方帳號領取優惠」「烘焙免費教學，加入LINE官方帳號領取食譜」這類正當商家貼文會整批誤報。實作上是先收齊四型提及的區間，再逐次檢查詞的出現位置有沒有落在區間外。

反過來，兩類詞單獨出現在 Discord 社團、讀書會、實體社群的貼文裡都很常見，缺了 LINE 提及一律不成立。

### 2.3 話術詞（pitch）

- **強詞**（可與錨點構成第三條路）：黑馬股、報明牌、代操、帶單、飆股、穩賺、獲利分享。
- **弱詞**（列入證據供人判讀，**不構成任何命中路徑**，兩個弱詞相加也不成立）：明牌、免費教學、不收費。

弱詞降權的理由：「免費教學」「不收費」在補習、餐飲、健身、公益貼文裡是中性詞；「明牌」單獨出現時多半指樂透或廟口明牌，辨識力遠低於「報明牌」。另外，否定語境照樣算證據——「不報明牌、不收費、不代操」正是這類貼文的標準開場白。

被其他命中詞包含的短詞會去重（「明牌」被「報明牌」包含時只留長詞），避免同一段文字被重複計數。

### 2.4 負向邊界

「賴」在中文裡是姓氏也是常用動詞，誤殺成本遠高於漏抓，因此提及本身就要排除下列語境：**信賴、依賴、無賴、仰賴、倚賴**——「我信賴：這個品牌」後面的冒號是正常標點，不是 LINE 帳號引導，而這種句子很可能同時帶投資詞，光靠話術詞的二次確認擋不住。「賴」「籟」單獨出現（賴清德、賴床、籟聲）一律不算提及，配上群組詞也不命中。

帳號型錨點的繫詞是封閉清單，不是任意字：`LINE Pay ID：abc123` 的 `Pay` 不在清單裡，樣式在那裡就斷開——LINE Pay 的收款 ID 不是加好友帳號（v4／D42）。

排除清單刻意只列這五個字。真實招攬句（例如「我的賴：某帳號」）前面同樣是中文，把規則擴成「前面是中文就不算」會整組漏抓。片語型限定「加入／加我」也是同一個考量——只認「加賴」會把「加賴床」一起收進來；「加 LINE」不受此限，因為 LINE 是專名，沒有那種歧義。

`LINE` 是英文詞的常見片段，單字型與帳號型都要求前面不接英文字母、單字型連後面也不接：**ONLINE、deadline、LINEUP、headline** 都不算提及。加入詞表刻意不收「加 LINE／加LINE」——片語型提及的區間本來就蓋住它，留著只會從 `加LINEUP`、`加LINEAR` 這類英文詞洩漏出來（片語型有後綴的負向邊界，純字串比對的詞表沒有）。

連結型網域的前面不得黏著英數、點、`@` 或斜線：**xxline.me/ti/g/x**、**9lin.ee/x**、**a.linktr.ee/x** 都是別人的網域，不是 LINE 的深連結。

### 2.5 正規化

比對前先把全形英數與全形標點（U+FF01–FF5E）平移成半形，再跑正則：招攬帳號會用全形英數規避純 ASCII 的帳號樣式。群組詞與加入詞的比對另外把 ASCII 小寫平移成大寫（「加line」也算加入詞）。兩種平移都只用於比對——換算後字串等長且逐位對齊，因此正則取得的位置可以直接套回原文切片，**證據片段保留使用者實際看到的全形字元**，好讓人一眼看出對方用了規避字元。控制字元與 bidi 字元在掃描前一併剝除（片段會寫進 storage 也會進選項頁 DOM）。

### 2.6 判定結果

偵測回傳 `{ hit, anchorMatch, pitchMatches, snippet, signals, lineId }`（`lineId` 為 v4／D43 新增，見 2.7）。`pitchMatches` 與 `hit` 分離：未命中時照樣回報有哪些話術詞，方便除錯與日後調參；`signals` 列出這次踩到的訊號類別，回溯判定走的是哪一條路。`anchorMatch` 與 `snippet` 只在 `hit` 為真時有意義。

`detectScamPitch` 會回報的訊號共八類（`SCAM_SIGNALS` 的前八個值），各自語意：

| 訊號 | 語意 |
|---|---|
| `link` | 命中連結型錨點（LINE 深連結／`lin.ee`／`linktr.ee`） |
| `line` | 有任一形式的 LINE 提及（連結／帳號／片語／單字四型任一） |
| `group` | 踩到獨立於提及本體之外的群組詞 |
| `join` | 踩到獨立於提及本體之外的加入詞，或命中暗號型行動呼籲樣式 |
| `pitch` | 踩到至少一個話術詞（強或弱） |
| `account`（v4） | 命中帳號型錨點（提及裡帶著帳號段） |
| `phrase`（v4） | 命中片語型錨點（加好友祈使句，不帶帳號段） |
| `id`（v4） | 抓到對方的 LINE 帳號本體（`lineId` 非空） |

第九類 `id-match`（v4／D46）不由 `detectScamPitch` 產生，只由 `scam-guard.js` 在 ID 跨帳號那條路成立時另外補上（見上方「路徑」表與 2.7），語意是「這次是靠索引比對成立，不是文字本身踩到的訊號」。

提及取用優先序為連結 > 帳號 > 片語 > 單字，多種形式並存時挑帶帳號本體的那一個當 `anchorMatch` 與證據片段的中心，證據卡才看得到對方的 LINE 帳號。片段取提及起點前後各 40 字（提及本體算在後半，窗格不隨其長度延伸，否則帳號後面緊接的長串英數會被整段拖進片段），儲存上限同為 120 字。v4 起，抓到 `lineId` 時這個中心改成 ID 本體本身（見 2.7），使用者一眼看到的是對方的帳號，而不是「LINE：」那三個字。

### 2.7 LINE ID 擷取與跨帳號索引（v4）

`detectScamPitch` 另外回傳 `lineId`：這段文字裡對方的 LINE 帳號本體，**未命中也照樣回報**——上方「ID 跨帳號」那條路就是靠這一欄，命中才回報的話那條路永遠走不到。

擷取依序試三段，前一段抓得到就不看後面（同一串同時出現多種來源時，證據卡要標寫得最明確的那一個）：

1. **帳號型錨點的帳號段**（`賴：xxx`、`LINE ID：xxx`）——寫得最明確。
2. **LINE／賴提及本體結尾起 80 字內（`SCAM_LIMITS.ID_WINDOW`）的「ID／帳號／號碼＋冒號＋帳號段」**。視窗自提及本體的**結尾**起算，不是整段文字起算：超出視窗的 ID 欄位（訂單 ID、會員 ID）視為與這次的 LINE 提及無關。
3. **加好友深連結的路徑段**——只認 `ti/p` 與 `lin.ee`；`ti/g` 的路徑段是群組邀請 token，不是個人帳號，取了只會用一串誰都對不上的鍵把無關的人拖進 `lineIdIndex`。前導 `~`（深連結寫法）不算帳號本體。

抓到的帳號段一律正規化：轉小寫、裁到 LINE ID 官方上限 20 字、剝掉尾端的 `.`／`_`／`-`（句讀不是帳號的一部分），剝完短於 3 字視為誤判，整段當作沒抓到。

暗號型行動呼籲（見 2.2）裡的代碼**不算 ID**——「傳「177」給我」的 `177` 只進行動呼籲判定，不進 `lineId`：暗號是雙方約定的一次性代碼，不是對方的帳號，寫進跨帳號索引只會製造誤連。

命中且抓到 `lineId` 時，`anchorMatch` 與 `snippet` 的中心改成 ID 本體（見 2.6）；`hit` 為假但靠 ID 跨帳號成立時，`detectScamPitch` 本身不產生 `anchorMatch`／`snippet`，改由 `scam-guard.js` 以 `lineId` 在原文中的位置另行裁切（同一套 40／120 字視窗，函式 `snippetAroundLineId`）。

## 3. 資料來源

| 用途 | 來源 | 網路請求 |
|---|---|---|
| 作者數字 id、帳號、顯示名稱、串文長度 | 詳情頁**伺服器預載資料**（頁面內 `script[type="application/json"]`，以網址列的貼文代碼比對，避免拿到同頁推薦的其他貼文） | 零 |
| 串文各篇文字 | 頁面 DOM 的貼文容器，以**作者帳號過濾**（他人回覆也是同一種容器，不算進串文） | 零 |
| 各篇的**貼文發布時間** | 該卡的 `<time datetime>`，只認「所屬連結的貼文代碼等於本卡代碼」的那一顆（轉發標頭之類的區塊會在同一個容器裡掛上指向**別篇**的時間）；`Date.parse` 解析失敗就不帶這一欄 | 零 |
| 作者數字 id（備援） | 作者 id 在預載資料缺席時，對**該貼文的永久連結**做一次匿名請求，從回應取作者數字 id | 每篇貼文 24 小時最多一次 |

DOM 取值只認**使用者看得到的貼文容器**：由河道以 SPA 進入詳情頁時，Threads 不拆掉河道那一層 DOM，而是把它留在文件裡（祖先帶 `hidden` 屬性與行內 `display:none`），同一則貼文因而有兩張貼文代碼相同的卡片，看不見的舊卡文件序還在可見主文卡之前。串文取值、標記補回與警示名單查表三條路都會跳過隱藏子樹內的容器，判定文字與標記只落在可見的那一張。

比對用的主鍵是**數字 id** 而非帳號：對方改名換帳號仍然認得出是同一個人。警示名單另存一張「帳號 → id」的反查表，河道上只有帳號可用時靠它查表。

備援請求的約束：

- `credentials: 'omit'`，**不帶登入憑證**、不帶 cookie，也不帶可辨識使用者的資訊；請求對象就是使用者當下正在看的那一篇貼文本身。
- `redirect: 'error'`，**不跟隨轉址**：這支請求要的是那一篇貼文自己的回應內容，不是最終網址（跟隨轉址是分享短碼還原那條路的事）；跳出去的轉址一律算失敗，不跟著落到登入頁或驗證頁再去解析別人的 HTML。
- 回應必須先自證**文件身分**才採信該 id（交叉驗證），避免拿錯人：回應裡 `og:url`／`al:android:url` 的永久連結正規化後必須等於請求的那一篇（帳號不分大小寫），確認「拿回來的這份 HTML 就是我要的那一篇」，且回應內的作者 id 候選必須全部同值。身分標籤指向另一篇時一律不採信，這道否決優先於下一項。
- 回應沒有任何可正規化的身分標籤時（登入態或舊形狀的回應），退回舊判準：作者 id 前後各 2000 字內要找得到相符的**帳號名稱**。登出態的回應整份不帶帳號名稱，只有文件身分認得出那一篇。
- 非 2xx 回應一律不採信——錯誤頁的內容不是貼文本身，不得拿來背書任何 id。
- 同一篇貼文 24 小時內只發一次，另有每分鐘的全域上限；節流表本身也有筆數上限與過期淘汰。
- 總開關關閉時**一律不發**。
- 請求以 `AbortSignal.timeout()` 設逾時，不讓挂住的連線一直佔著節流名額；這支 API 自 Chrome 103 起才有，manifest 的 `minimum_chrome_version: "103"` 就是由它而來。
- 取不到 id（請求失敗、交叉驗證不過、逾時）時，頁面上仍掛標記，但**不寫入警示名單**——沒有穩定主鍵的條目會破壞名單語意。

處理輸入時的防呆上限：身分標籤（`og:url`／`al:android:url`）只掃回應的前 64 KB——meta 標籤在 `<head>` 裡，離文件開頭很近，再往後掃只是對整份頁面跑無界正則；作者識別碼則掃前 1 MB（登出態的回應實測約 581 KB，作者 id 落在文件中後段，上限太低會把它整段切在範圍外；仍保留天花板，不對超大回應做無界正則掃描）。預載資料的走訪另有深度與節點上限——頁面餵進來的是任意 JSON，沒有上限時畸形或刻意加深的結構會把主執行緒卡住。

## 4. 儲存形狀與上限

`chrome.storage.local.scamBlocklist`：

```js
{
  version: 2,
  entries: {
    [userId]: {
      state,         // 'active'（在名單上）｜'dismissed'（使用者解除過，不再自動加回）
      dismissedAt,   // 解除當下的時間；state 為 'active' 時不寫這個鍵
      handle,        // 原樣帳號（不帶 @）
      displayName,
      // postUrl／snippet／at 為必要欄位，其餘八欄選填（見下方正規化規則）
      evidence: [{ postUrl, snippet, at, anchorPostUrl?, threadUrl?, anchorMatch?, signals?, postedAt?, rulesVersion?, deviceId?, lineId? }],
      addedAt,
      updatedAt,     // 任何欄位變動（含解除／復原）都更新；雲端同步的 LWW 判準
      source,        // 'auto'（掃描命中）；'manual' 為保留值，本版不產出
      pushAfter,     // 選填：本機專有的推送提示。被動再掃到已列名的作者時只併證據、
                     //   不推進 updatedAt，新證據的時間記在這裡，讓雲端同步的選批水位線
                     //   （取它與 updatedAt 的較大者）還選得到這一筆。**永不上雲**：
                     //   Mark 是固定九欄的跨端契約，多一欄後端整筆拒收。推送成功後
                     //   不回收，只靠水位線覆蓋；值本身在 scam.hit 驗證時就夾成
                     //   min(at, now)，未來時戳會變成推不動的 marks 水位線
    },
  },
  handleIndex: {},   // handle 小寫 → userId 的反查表，一律由 entries 重建，
                     //   且只收 state === 'active' 的條目（已解除的不進索引）
}
```

v1 的頂層 `allowlist` 在 v2 **不再是儲存狀態**：「已解除」不再是另一張表，而是同一筆條目的 `state`，**證據照樣保留**——復原當下立刻有內容可看，不必等下一次命中才長回來。選項頁的「已解除」小節改由 `entries` 中 `state === 'dismissed'` 的條目派生（讀者可直接用 `normalizeScamBlocklist` 掛出來的唯讀 `allowlist` 視圖，見下方正規化規則），河道與詳情頁的查表則只認 `state === 'active'`。

v4（D46）另外派生一張 `lineIdIndex`（`{ lineId → userId }`），與 `allowlist` 同款——由 `normalizeScamBlocklist` 掛成回傳值上的唯讀可列舉鍵，只活在記憶體、不持久化、不上雲，只含 `state === 'active'` 的條目：一筆條目的每一格證據上有 `lineId` 就佔一個鍵，同一位作者換過幾個 ID 就佔幾個鍵，讓同一個 ID 換一個帳號再招攬一次照樣認得出來（用途見 2.6「ID 跨帳號」路徑）。狀態併進同一個物件也是雲端同步的前提：名單與白名單各存一邊時，同一位作者在雲端會是兩筆互不相干的資料，最後寫入者勝（LWW）沒有共同的比較對象（見 `docs/cloud-sync.md` 決策 D36）。

**v1 → v2 遷移**：原 `entries` 的每一筆轉成 `state: 'active'`；原 `allowlist` 的每一把鍵轉成 `state: 'dismissed'` 的條目（沒有證據，`dismissedAt` 取原本的 `at`，`addedAt` 同值）；同一位作者在兩邊都出現時以 `allowlist` 為準（解除是較晚、較明確的決定），證據保留。`updatedAt` 缺席時以 `addedAt`／`at` 補。遷移後的筆數一樣受下方上限約束。

另有 `chrome.storage.local.scamGuardEnabled`（總開關，缺席視為開啟）。

備援請求的節流狀態另存兩把鍵，**一律寫 `chrome.storage.session`（環境沒有 session 空間時退回 `local`），瀏覽器關閉即清**：

| 鍵 | 內容 | 上限 |
|---|---|---|
| `scamAuthorFetchAt` | 以貼文網址為鍵的最近請求時間，撐起「同一篇貼文 24 小時只發一次」 | 500 筆，超過或滿 24 小時即淘汰 |
| `scamAuthorFetchLog` | 近一分鐘內發出的請求時戳，撐起每分鐘的全域上限 | 只留一分鐘內的時戳 |

這兩把鍵是節流狀態，不是使用者資料：只記「這個網址剛問過」與「剛才問了幾次」，**一律不上傳、不隨雲端同步**（名單本體則可隨雲端同步，見 `docs/cloud-sync.md` D35–D40）。

| 上限 | 值 | 說明 |
|---|---|---|
| 名單筆數 | 5,000 位作者 | 依 `updatedAt` 降冪保留，最舊的先淘汰（**v2 起不看 `addedAt`**：解除、復原與證據補寫都會推進 `updatedAt`，用它淘汰才會留下使用者最近真的碰過的條目）。`state: 'active'` 與 `state: 'dismissed'` **共用同一個 5,000 名額**，不分開計數——v1 的 `MAX_ALLOWLIST` 廢止（常數保留，不再作為獨立天花板） |
| 每位作者的證據 | 3 筆 | 依時間降冪保留最新的；同一篇**錨點貼文**不重複記（去重鍵 `anchorPostUrl ‖ postUrl`）——同一串被從不同篇重新打開時 `postUrl` 是不同的一頁，錨點篇卻是同一篇，綁 `postUrl` 會讓同一次招攬吃掉三筆額度 |
| 證據片段 | 120 字 | 儲存與顯示同一道天花板 |
| 整包軟預算 | 2 MB | 以序列化後的 UTF-8 **位元組**計，超出即續裁最舊的條目。分母是 `chrome.storage.local` 的配額：Chrome 114 起為 10 MB，2 MB 約佔兩成；更早的版本為 5 MB，此時約佔四成。manifest 的下限 Chrome 103 落在 5 MB 配額的那幾版，四成仍在安全水位。證據放滿時實際可容約 900–1,600 位作者（證據補上錨點貼文／串頭連結、錨點本體、訊號與貼文發布時間後，每筆條目約增 45%），筆數上限先到或預算先到都會觸發淘汰。`state: 'dismissed'` 的條目**一併計入**這 2 MB 預算——它們與 active 條目存在同一個物件裡，不算進來就會低估實際佔用 |

正規化規則：`normalizeScamBlocklist` 從 storage 讀回時一律重算成 `version`／`entries`／`handleIndex` 這三把鍵的形狀（讀到 v1 的 `allowlist` 先跑上方的遷移），未知欄位不保留；另在回傳值上掛兩份唯讀派生視圖，讓既有讀者不必同時改寫：一份是由 `state === 'dismissed'` 的條目**派生的 `allowlist`**（形狀維持 v1 的 `{ [userId]: { at, handle } }`，`at` 取 `dismissedAt`）；另一份是 v4（D46）新增的 **`lineIdIndex`**（`{ lineId → userId }`，只含 `state === 'active'` 的條目，由每筆條目證據上的 `lineId` 逐格派生，鍵一律小寫），與 `allowlist` 同款掛成普通可列舉鍵。這兩份視圖都是相容層、不是儲存狀態：`capScamBlocklist` 在落盤前一律把它們拿掉，**storage 裡只有三把鍵**——留著就會變成第二份真相，`lineIdIndex` 尤其不能落盤，下一輪讀回會把它當成未知欄位剝除、白算一次。`handleIndex` 永遠由 `entries` 重建，不信任存下來的反查表（否則會留下指向已刪條目的孤兒鍵），且**只收 `state === 'active'` 的條目**：反查表的用途是河道上拿帳號查「這個人在不在名單上」，已解除的作者本來就不該被標記，進了索引等於把解除過的人又標一次；原型污染用的鍵一律拒收；`entries` 的鍵必須是 userId 形狀（純數字字串、1–20 位），不符的整筆剝除——鍵不驗形狀時，任意字串都能混成一筆永遠對不上寫入側 userId 的幽靈條目。`state` 只接受 `'active'`／`'dismissed'`，不在枚舉內的整筆視為 `'active'`；`dismissedAt` 非有限數字即剝欄，`state` 為 `'dismissed'` 而 `dismissedAt` 缺席時**補 0**（不拿 `updatedAt` 充當——那是「最後一次動過」，不是「什麼時候解除的」，用它充當會讓一筆來歷不明的解除混進最近解除的那幾筆裡）：解除時間不明的條目寫 0，在「已解除」小節依時間降冪時自然排到最後；`addedAt`／`updatedAt` 只要有一個合法就以合法的那個補另一個缺失的欄位（例如 `updatedAt` 非有限數字時以 `addedAt` 補，反之亦然），兩者都不合法才丟棄整筆（R3-14）。`pushAfter` 是本機專有欄位，只放行有限數字、形狀不合就不落鍵；它參與整包的位元組預算，但 `toScamMark` 不送、`fromScamMark` 不讀回，跨裝置合併時保留本機那一邊的值（見 `docs/cloud-sync.md` §3.1 CR-1）。

單筆證據的八個選填欄位另有一組規則，**形狀不合只剝該欄、不剝整筆**——它們是加值資訊，不是證據成立的必要條件，為了一個壞掉的 `threadUrl` 丟掉整筆等於把使用者真的命中過的紀錄一起抹掉。`postUrl` 與 `at` 仍是必要欄位，不合法整筆丟棄。**缺席時輸出不帶該鍵**（不補 `null` 也不補空字串）：選項頁靠「鍵在不在」決定要不要畫那一行，補空值會讓舊證據畫出一排空連結。

| 欄位 | 意義 | 正規化 |
|---|---|---|
| `postUrl` | 使用者當時開的那一頁（必要） | 走 `normalizePostUrl` 白名單，不合法整筆丟棄 |
| `anchorPostUrl` | 含錨點那一篇的永久連結 | 走 `normalizePostUrl`，不合法剝欄 |
| `threadUrl` | 串頭（第一篇）的永久連結 | 走 `normalizePostUrl`，不合法剝欄 |
| `anchorMatch` | 錨點本體，供選項頁做片段高亮 | 非字串剝欄；剝控制／bidi 字元後硬裁 **40 字**（上限在儲存端保證，顯示端不再截） |
| `signals` | 這次踩到哪幾類訊號 | 逐項過白名單 `link｜line｜group｜join｜pitch｜account｜phrase｜id｜id-match`（v4 起九類，見 2.6），去重並輸出固定順序；非陣列或全被剝光時**整欄剝除，不留空陣列**（留空陣列會讓證據卡畫出一排沒有 chip 的空白） |
| `postedAt` | 貼文發布時間（毫秒；`at` 是掃到的時間，兩者語意不同） | 非有限數字剝欄——補 0 會在證據卡上畫成 1970 |
| `rulesVersion` | 命中當下的規則版本（`SCAM_RULES.version`，**數字**），跨裝置看得出這筆是哪一版規則判的 | 非有限數字剝欄 |
| `deviceId` | 回報這筆證據的裝置（沿用 `syncDevice.deviceId`，未登入時缺席） | 只認 UUID 形狀、一律存小寫，形狀不對剝欄 |
| `lineId`（v4／D44） | 對方的 LINE 帳號本體，**本機專有**：不上雲（`toScamMark` 不送、`fromScamMark` 不讀入），跨裝置合併時保留本機那一邊的值（`mergeScamEvidencePair`，與 `snippet`／`anchorMatch`／`postUrl` 同一組本機專有欄位） | 走 `normalizeScamLineId`——與 2.7 擷取時用的 `normalizeLineIdValue` 是兩把不同的尺，這裡刻意寬鬆：非字串或空字串整欄不落鍵，其餘一律轉小寫並裁到 20 字，不再檢查 3 字下限、也不剝尾端句讀；形狀不合只丟這一欄，為了它把一次真的命中整筆退掉是賠本生意 |

寫入權集中在 background：只有 background 寫 `scamBlocklist`，content script 與選項頁一律直接讀 storage 並監聽變更事件，避免多處併寫互相覆蓋。

## 5. 介面行為

- **貼文詳情頁**：命中時在主文作者列時間右邊掛一枚標記，找不到作者列的時間連結時退回互動列上方（文案 `scamTagLabel`：「LINE 群組引導」，滑鼠提示 `scamTagTooltip`：「這串貼文含引導加入 LINE 或群組的字句，常見於投資招攬。請自行判斷，勿輕易加好友或提供個資。」），使用警告色而非錯誤色。
- **首次提示**：該次瀏覽階段第一次成功加入警示名單時跳一次 toast（`scamFirstHitToast`），告知已加入本機警示名單、可在設定頁管理；之後不再重複打擾。
- **河道**：只標記已在警示名單裡的作者，靠帳號反查表比對，不做全文掃描。
- **選項頁警示名單卡**（「警示名單」分頁，選項頁三分頁的最後一頁）：每位作者一張卡，**整張卡就排成一則貼文的樣子**（比照 Threads），使用者在名單裡看到的與當初在站上看到的是同一個形狀。
  - **卡頭另有一則雲端額度提示**（`#scamEvictedHint`）：免費方案雲端保留額度用罄、有筆數因此被淘汰時（`syncState.marksEvicted > 0`）在卡頭計數旁常駐顯示「雲端已達免費額度，較舊的 N 筆只保留在本機」；`marksEvicted` 是插件端的累計筆數，沒有淘汰過時整條隱藏；歸零與夾上限的時機見 `docs/cloud-sync.md` §3.1「雲端淘汰」（R3 縱深）。
  - **卡頭標題右邊有一顆資訊鈕**（Lucide `info` 圖示），點開「這個功能怎麼運作」說明視窗：五段條列，講清楚「只在你點進貼文時掃描」「命中就掛標記並記下作者」「河道只查表不掃文」「名單跟著你的帳號走：預設留在本機，開啟雲端同步後作者帳號、顯示名與證據貼文網址會上傳到開發者後端，貼文文字片段留在本機」「判定是規則比對，可能誤判」。這是一份對真人帳號的負面標記，使用者有權知道它憑什麼下判斷、資料落在哪，以及它會出錯時該怎麼推翻。視窗沿用既有 overlay／modal，可由 ✕、點遮罩或 Esc 關閉，關閉後焦點回到資訊鈕，Tab 焦點鎖在框內。
  - **一筆證據 ＝ 一則貼文**，就作者列與本文兩列；由同一個建構函式產出，主卡那一筆與對話框裡的每一筆結構與樣式完全相同，不存在第二套渲染：
    - **作者列**：顯示名稱與 @帳號（整塊是連到作者頁的連結，新分頁開啟；沒有顯示名稱時只顯示帳號，不用帳號充當顯示名再重複一次）→ **時間**（緊接帳號之後的小字灰，**本身就是該篇的永久連結**，`anchorPostUrl ‖ postUrl`，新分頁開啟、`rel="noopener noreferrer"`）→ **標記 pill**（文案 `scamTagLabel`，與內容腳本掛在貼文上那顆相同）。
    - **本文**：完整片段不截斷（儲存端已保證 ≤120 字），`anchorMatch` 以 `<mark>` 高亮（暖色淡底並繼承文字色，不吃瀏覽器預設的螢光黃）。選項頁不另外判斷標亮誰——`anchorMatch` 是什麼就標什麼；標亮**以 ID 本體優先、抓不到才退回片語**這件事在寫入端（`detectScamPitch`，見 2.6／2.7）就已經決定，選項頁只是原樣呈現。純靠 ID 跨帳號成立（見 2.6「ID 跨帳號」路徑）的那筆證據沒有話術串文可標，`anchorMatch` 與片段一律以抓到的 `lineId` 為中心。雲端同步讀回的證據沒有 `snippet`（片段只留在掃到它的那台裝置，見 D40）時**不是留白不畫**，而是改掛 `span.scam-evidence-missing` 的灰字佔位說明（文案 `opScamEvidenceMissing`），作者列與時間、標記 pill 照常呈現。
    - 本文下方**沒有第三列**：回串頭的「整串 ↗」連結與訊號 chips 都不畫——證據貼文連的就是錨點那一篇，回串頭是 Threads 自己的事，卡上多一條連結只是把兩個去處擺在一起讓人猶豫；訊號則是判定的內部分類，使用者看片段本身就知道為什麼被標記。`threadUrl` 與 `signals` **照存不動**（它們是證據的一部分，也還有除錯與日後調參的價值），只是不畫。
  - **時間格式照 Threads**：未滿一分鐘「剛剛」、未滿一小時「38分鐘」、未滿一天「3小時」、未滿七天「5天」（數字與單位之間不留空白、不帶「前」字；en 為 `now`／`38m`／`3h`／`5d`），**滿七天改絕對日期 `YYYY-MM-DD`**——「400天」對使用者沒有意義。取的是該篇的 `postedAt`，缺席（舊證據）退回 `at`。絕對日期與貼文代碼尾 6 碼一律留在 `title` 上（相對時間看不出是哪一天，同一段招攬文案貼了好幾篇時也靠代碼分辨各篇）；連結文字只有一段時間，讀屏讀不出它連去哪，另補 `aria-label`。
  - **主卡只放最新一筆證據**：一張卡上同時擺三段完整片段太重。列的右上角、緊貼「⋯」鈕左邊有一段小字「命中 N 篇」，點下去開對話框逐筆列出全部證據（內容區可捲動）；**只有一筆時不畫**——對話框裡看到的就是卡上那一筆。篇數講的是整位作者，因此不進證據組件，對話框裡也不逐筆重複。對話框標題為「顯示名 @帳號 · 命中 N 篇」，可由 ✕、點遮罩或 Esc 關閉，關閉後焦點回到那顆按鈕，Tab 焦點鎖在框內。
  - **卡片右側是「命中 N 篇」與「⋯」選項鈕**：後者沿用紀錄卡的三點圖示與選單樣式，目前只放「解除」一項（danger 色，circle-minus 圖示，與刪除紀錄的垃圾桶區隔），二次確認後把該筆條目改成 `state: 'dismissed'`，移進「已解除」小節。
  - 名單**不對外抓頭像**（那會讓選項頁替每一列向 Threads 發一次請求），因此沒有頭像欄位；加入名單的時間（`addedAt`）**照存但不顯示**——使用者要判斷的是這篇招攬貼文本身，不是自己什麼時候滑到它。
  - 證據**逐筆呈現不合併**：一位作者最多三筆，在可捲動的對話框裡各自成列不會擁擠，合併反而會讓「每筆一個節點」這條共用結構破例。
  - 全卡零 `innerHTML`：顯示名稱與片段都是他人貼文帶進來的字串，一律 `createElement`／`textContent`；`anchorMatch` 的高亮以 `indexOf` 切前中後三段各自建文字節點。帳號串進作者頁網址前整段走 `encodeURIComponent`。
  - 「已解除」小節列出 `state: 'dismissed'` 的條目，可「復原」把作者移回可被偵測的狀態。
  - **總開關關閉時分頁照常可見可編輯**：名單本體與「已解除」小節都留著，解除與復原照常運作（也照常更新 `updatedAt`）；狀態列 `#scamDisabledBar` 加在**卡頭之後、名單清單之前**（`.scam-blocklist` 卡片內，卡頭含標題、資訊鈕、計數與雲端額度提示），內容為「LINE 群組引導警示已關閉——名單不會同步，也不會在河道掛標記」，右側一顆「開啟」鈕直接把總開關打開。這個分頁只有這一張卡，狀態列因此在視覺上仍落在整頁最上緣。關閉期間不掃描、不掛標記、不同步（D35）。
  - 空狀態顯示「警示名單目前沒有作者」（en `Warning list is empty`），計數為零時顯示「0 位作者」。
- **設定卡**（「總覽」分頁）：總開關「LINE 群組引導警示」，說明文案（`opScamGuardDesc`）只講功能本身：「偵測引導加入 LINE 群組的串文，並在貼文上標記」，落點細節留給名單卡的資訊鈕說明視窗（見上方「卡頭標題右邊有一顆資訊鈕」第四段）。「管理警示名單」同頁錨點（`#flags` 切到警示名單分頁）與標題同一行、貼在標題右側，小字連結樣式，後接 Lucide `arrow-right` inline SVG（14px、`stroke="currentColor"`、`aria-hidden="true"`，取代原本的「→」字元）；開關維持在列最右不動，窄寬度時連結整個換到標題下一行，不推動開關或標題。

介面文案中英雙語，跟隨既有的介面語言設定。

## 6. 訊息協議

content script 與選項頁都不直接寫名單，一律送訊息給 background。

| 訊息 | 方向 | 內容 | 回應 |
|---|---|---|---|
| `scam.hit` | content script → background | `{ userId｜null, handle, displayName, postUrl, snippet, anchorMatch, pitchMatches, at, anchorPostUrl?, threadUrl?, signals?, postedAt?, lineId? }` | `{ ok: true, added, entry }`；作者已解除（`state: 'dismissed'`）時回 `{ ok: true, added: false, allowlisted: true }` |
| `scam.blocklist.remove` | 選項頁 → background | `{ userId, handle?, displayName? }` | `{ ok: true }`，把該筆條目改成 `state: 'dismissed'`、寫 `dismissedAt`／`updatedAt` 並重建反查表。名單裡沒有這一筆時補建一筆空的 dismissed 條目，並寫入訊息帶來的 `handle`／`displayName`（`handle` 一律驗 `^[A-Za-z0-9._]{1,80}$`，形狀不合只忽略該欄位、解除照常成立）——缺 `handle` 的 mark 上雲會被後端整筆拒收，那次解除從此同步不出去 |
| `scam.blocklist.restore` | 選項頁 → background | `{ userId }` | `{ ok: true }`，把該筆條目改回 `state: 'active'`、清掉 `dismissedAt`、更新 `updatedAt` |

失敗一律回 `{ ok: false, code }`：

| 回應碼 | 情境 |
|---|---|
| `bad_request` | 欄位形狀不合（帳號或貼文網址格式不對、片段超長、id 不是純數字字串、時間不是數字）；證據補強的五欄有帶但形狀不合亦同——`anchorPostUrl`／`threadUrl` 過不了貼文網址白名單、`anchorMatch` 非字串或超過 40 字、`signals` 非陣列或含白名單外的值、`postedAt` 非有限數字 |
| `no_user_id` | 預載資料沒有作者 id，備援也取不到——頁面照樣掛標記，但不入名單 |
| `disabled` | 總開關關閉，不寫入也不發請求 |
| `internal_error` | 讀寫本機儲存失敗 |

`anchorPostUrl`／`threadUrl`／`anchorMatch`／`signals`／`postedAt` 五欄**一律可缺席**（舊版 content script 送來的三欄 payload 照常受理），但**有帶就驗形狀，不合格整筆回 `bad_request`**，而不是默默剝掉：payload 是自家 content script 送的，形狀不對代表兩端版本對不上，默默吞掉會讓錯誤晚好幾週才被發現。通過驗證的五欄一路寫進 `entry.evidence[0]`。證據的第六與第七個選填欄位 `rulesVersion`／`deviceId` **皆不由 content script 送**，而是 background 寫入當下補上——`rulesVersion` 取當下的 `SCAM_RULES.version`（數字，不是版本字串），`deviceId` 取 `syncDevice.deviceId`（未登入、還沒產生裝置識別碼時整個鍵不寫）——規則版本與裝置身分都是 background 的資料，讓頁面端送等於多開一條可被偽造的入口。`anchorMatch` 在送出端就先裁到 40 字——連結型錨點（`lin.ee`／`linktr.ee`／`line.me` 深連結）的帳號段沒有長度上限，不裁的話一次真的命中會整筆被擋下。

`lineId`（v4／D43、D44）是這條「有帶就驗形狀，不合格整筆回 `bad_request`」規矩的**唯一例外**：形狀不對（非字串或空字串）只丟這一欄、payload 整筆照收，走 `normalizeScamLineId`（見第 4 節）。它是加值資訊（標亮位置、`lineIdIndex` 的唯一真相來源），不是證據成立的必要條件，為了它把一次真的命中整筆退掉是賠本生意。

`remove` 與 `restore` 在 v2 都不再搬家、也不刪資料：兩者都只改同一筆條目的 `state`，**證據原封保留**（`remove` 不清 `evidence`，`restore` 也不必重新累積）。條目只有在使用者清空整份名單、或撞到上限被淘汰時才真的消失。兩則訊息一律更新 `updatedAt`——它是雲端同步的 LWW 判準，漏更新會讓另一台裝置的舊狀態反過來蓋掉這次的決定（見 `docs/cloud-sync.md` 決策 D37）；總開關關閉期間照樣更新，重新開啟後才與雲端合併（D35）。

`scam.hit` 撞到 `state: 'dismissed'` 的條目時維持既有語意：不改 `state`、不加回名單，回 `{ ok: true, added: false, allowlisted: true }`。

`pitchMatches` 仍只是讓判定依據與命中同時可見（除錯、日後調參），background **不取用、也不落盤**。

訊息來源會驗證：`scam.hit` 只接受來自 Threads 分頁的 content script，名單管理訊息只接受來自本擴充功能頁面。

## 7. 誤報處置

誤判由使用者一鍵推翻，而且**推翻就是終局**：

1. 在選項頁警示名單卡按「解除」，二次確認。
2. 該筆條目改成 `state: 'dismissed'`，移出名單本體、落到「已解除」小節，證據照樣保留。
3. 之後再次掃到同一位作者的貼文，**不會自動加回**——偵測仍會判定，但寫入端看到 `dismissed` 就直接短路，回報「已在白名單」。
4. 若使用者反悔，可在「已解除」小節按「復原」，把條目改回 `state: 'active'`、恢復成可被自動加入的狀態。
5. 已登入雲端同步時，解除與復原都會更新 `updatedAt` 並跟著同步出去，其他裝置照 LWW 收斂到同一個判斷（`docs/cloud-sync.md` D36／D37）。

設計取向：誤殺成本高於漏抓。被誤標的是一個真人帳號，標錯會讓使用者不信任整個功能；漏抓只是回到沒有這個功能的狀態。所有調參（雙訊號門檻、群組／加入詞的獨立性要求、弱詞降權、負向邊界）都往同一個方向倒。

## 8. 已知限制

- **正當招攬也可能誤報**：規則以行動呼籲詞為門檻，只要 LINE 提及＋「拉你進群／加入／私訊我」這組動作同時出現就成立，因此正當的社團、讀書會、商家私訊招攬照樣可能被標記。這是把門檻放在動作而非話術的必然代價；使用者可以在警示名單上一鍵解除，解除後條目落到「已解除」小節，不再自動加回。
- **SSR 資料可被注入指定作者識別碼**：作者 id 取自頁面的伺服器預載資料，若 Threads 自身出現 HTML 注入漏洞讓第三方把假的預載資料塞進頁面，理論上可以讓警示名單記到指定的作者身上。前提是 Threads 頁面本身先被攻破，後果也限於使用者自己帳號底下的單一條目（不與其他使用者共享），使用者隨時可解除。
- **河道只標已知作者**：時間軸上不做全文判定，因此第一次遇到的招攬帳號要等使用者點進詳情頁才會被認出來。
- **只判自回覆串**：判定對象是作者自己的串文；引導文字若出現在他人回覆、圖片、影片或外部聚合頁內文，本版偵測不到。
- **圖片內、拆字、諧音的 LINE ID 抓不到**（v4）：`extractLineId` 只認文字裡連續的帳號字元序列，貼在圖片裡的 ID、刻意拆開（例如「賴：a b c」逐字插空白）或用諧音字規避的 ID 一概抓不到；這類貼文只能退回片語當 `anchorMatch` 與 snippet 中心，ID 跨帳號那條路也查不到，只剩行動呼籲與話術詞那幾條路還能命中。
- **規則是中文取向**：提及樣式與群組／加入／話術詞表針對繁體中文的招攬語境，其他語言的同類劇本不在本版範圍。
- **規則隨版本內建**：`SCAM_RULES` 這一版直接寫在前端程式碼裡，改詞表要跟著發版；由後端下發規則包是後續的事。
- **v1 不支援手動加入**：沒有數字 id 的條目會破壞名單主鍵的語意，因此不提供手動輸入帳號加入警示名單，延後評估。
- **同步有條件、片段不上雲**：名單的雲端同步**只在使用者已登入且總開關開啟時**進行——沒登入就只存在這台裝置，總開關關閉期間不拉也不推（重新開啟後才補做合併）。貼文文字片段（`snippet`／`anchorMatch`）與使用者當時開的那一頁網址（`postUrl`）**一律不上傳**，因此另一台裝置同步回來的證據只有連結與時間，命中對話框上那一筆畫不出片段本文，也沒有高亮。詳見 `docs/cloud-sync.md` 決策 D35–D40。
- **不跨使用者共享**：同步只發生在同一位使用者自己的帳號底下，沒有任何跨使用者的共享名單，匯出／匯入檔也不含名單——這是刻意的取捨，社群回報名單牽涉審核責任與濫用風險。
- **Threads 改版風險**：偵測依賴詳情頁的伺服器預載資料結構與頁面 DOM 結構，兩者都可能隨 Threads 改版而變動。降級行為是**靜默退場**：取不到預載資料就只靠 DOM 文字，取不到作者 id 就只掛標記不入名單，兩者都取不到就什麼都不做——絕不在資料不全時猜測歸屬，也不影響插件既有的連結淨化功能。
- **轉發卡跟著內容作者走**：河道上的轉發卡片以被轉發貼文的作者為準——中立帳號轉發被標記作者的貼文會被標記，被標記的作者轉發他人貼文則不會。判準是卡片上的貼文連結指向誰，不是誰按了轉發。
- **證據連結會失效**：證據指向原貼文的永久連結，貼文若被刪除或帳號被停用，連結會連不到內容；名單上的條目與片段仍保留在本機。
- **名單同步的容量與可觀測性限制另見 `docs/cloud-sync.md` 第 6 節**：雲端保留超過 2,000 筆時的回填停擺、回填中無可觀測狀態、後端證據聯集與淘汰時序等限制記在該節的 marks 相關條目，不在此重複。
