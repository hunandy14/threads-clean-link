# LINE 群組引導標記設計文件

本文件描述插件端「LINE 群組引導標記」的設計：使用者自己點進 Threads 貼文詳情頁時，就地判斷這一串貼文是不是「長篇投資心得＋末篇引導加 LINE」的招攬劇本，命中就把作者記進**只存在這台裝置**的標記名單，並在頁面上掛一枚標記。範圍限於插件端的偵測規則、本機儲存、訊息協議與介面行為。

## 1. 目的與範圍

投資招攬帳號的共通劇本是：正文經營人設、談投資獲利或職涯轉折，再在自回覆串的尾端留一個 LINE 提及，把人帶去私訊或群組。單看任何一半都可能是正常內容——交友貼文會留 LINE，讀書會也會揪人進群組——所以標記的判準是兩類訊號同時出現。目的是在使用者還沒加好友之前，把這個訊號擺到他眼前。

| 項目 | 設計 |
|---|---|
| 資料落點 | 標記名單、證據、白名單一律寫 `chrome.storage.local`，備援請求的節流表寫 `chrome.storage.session`（瀏覽器關閉即清）；**不上傳、不隨雲端同步、不進匯出檔**，也不做社群回報或跨使用者共享 |
| 觸發時機 | 只有使用者自己開啟某篇貼文的**詳情頁**才掃描該頁；不遍歷河道全文、不枚舉串文、不背景輪詢、不預先抓取 |
| 掃描對象 | 該頁已經送到瀏覽器的內容（伺服器預載資料與頁面 DOM），不另外向 Threads 索取串文內容 |
| 權限 | 沿用既有的 threads.com／threads.net content script 與 `storage` 權限，`manifest.json` 的**權限陣列零變更**；manifest 另新增 `minimum_chrome_version: "103"`（備援請求用的 `AbortSignal.timeout()` 自 Chrome 103 起才有）與 `tcl-core.js`、`scam-guard.js` 兩支 ISOLATED content script 新檔 |
| 總開關 | 選項頁設定卡「LINE 群組引導標記」，**預設開啟**；關閉後不掃描、不標記、不寫入，也不發出任何請求 |
| 判定位置 | 全部在本機完成，不呼叫任何伺服器做判斷，不含遠端程式碼、不含遠端規則更新 |

河道（首頁時間軸）不掃全文——整頁都是別人的貼文片段，掃了只會製造誤判。河道只做一件事：拿貼文卡片上的帳號去查本機標記名單，已知作者才標記。

## 2. 偵測規則

招攬串的共通結構不是投資話術，而是**「LINE 提及 ＋ 把人拉進群組／要人加好友」**這組動作——軟性招攬串（長篇心得鋪陳、末篇只留一句「加 LINE：xxx，我把你拉進群組」）整串一個話術詞都不放。命中因此走三條路：

| 路徑 | 條件 |
|---|---|
| 連結型錨點 | 深連結本身就是「加好友／加群組」的入口，單獨成立 |
| 提及 ＋ 行動呼籲 | LINE 提及 ＋（群組詞 或 加入詞） |
| 錨點 ＋ 強話術詞 | 連結／帳號／片語三型錨點 ＋ 至少一個強話術詞（既有路徑，保留） |

話術詞不再是任何門檻的必要條件，只列入證據（見 2.3）。

規則的詞表與正則集中在 `tcl-core.js` 的 **`SCAM_RULES`** 物件，`detectScamPitch(text, rules)` 的第二參數可選、預設就是它：規則是資料、判定是邏輯，後續可改為由後端下發規則包而判定邏輯不動。

### 2.1 LINE 提及（mention）

| 類型 | 樣式 | 可走哪幾條路 |
|---|---|---|
| 連結型 | LINE 加好友／群組深連結（`line.me` 的 `ti/p`、`ti/g` 路徑，含帶 `R/` 的舊式變體 `line.me/R/ti/p/`、`line.me/R/ti/g/`）、`lin.ee` 短網址、`linktr.ee` 聚合頁；`https://` 與 `www.` 都可省 | 三條都算，且可單獨成立 |
| 帳號型 | 「賴」「籟」「LINE」（`ID` 兩字可省）＋ 半形／全形冒號 ＋ 至少 3 位帳號字元（上限取 LINE ID 官方的 20 字） | 提及、錨點 |
| 片語型 | 加好友祈使句：「加入我的」「加入我」「加入」「加我的」「加我」＋ 賴／籟／LINE，以及不必帶這些前綴的「加 LINE／加LINE」 | 提及、錨點 |
| 單字型 | `LINE` 單字，前後都不接英文字母 | 只走「提及 ＋ 行動呼籲」，且只認主動招攬詞 |

`line.me` 的其他路徑（官網首頁、分享頁）不算連結型錨點，那些不是引導私訊的入口。連結型省掉 `https://` 是因為招攬文常直接寫「lin.ee/xxx」，Threads 自己會渲染成連結；省掉之後改以前置的負向邊界擋住黏在別的網域後面的情形（見 2.4）。

### 2.2 行動呼籲：群組詞與加入詞

- **群組詞**：群組、社群、群裡、進群、拉進、拉你進、小群。
- **加入詞**：加入、加我、私訊我。
- **主動招攬詞**（上兩張表的子集，描述「把你帶走」這個動作）：進群、拉進、拉你進、小群、加我、私訊我。

門檻**分兩層**：錨點型提及（連結／帳號／片語）已經帶著帳號或祈使句，吃完整的群組詞＋加入詞；**單字型提及只認主動招攬詞**。「群組」「社群」「加入」是名詞，公司公告、社區公告、讀書會、商家會員貼文本來就會跟 LINE 同框——「公司公告改用 LINE 群組發布」「LINE Pay 加入會員送點數」不該進標記名單。

兩類詞都**必須獨立於提及本體之外出現**。「加入我的 LINE」整段就是一個片語型提及，裡面的「加入」不得再充當加入詞——否則「加入LINE官方帳號領取優惠」「烘焙免費教學，加入LINE官方帳號領取食譜」這類正當商家貼文會整批誤報。實作上是先收齊四型提及的區間，再逐次檢查詞的出現位置有沒有落在區間外。

反過來，兩類詞單獨出現在 Discord 社團、讀書會、實體社群的貼文裡都很常見，缺了 LINE 提及一律不成立。

### 2.3 話術詞（pitch）

- **強詞**（可與錨點構成第三條路）：黑馬股、報明牌、代操、帶單、飆股、穩賺、獲利分享。
- **弱詞**（列入證據供人判讀，**不構成任何命中路徑**，兩個弱詞相加也不成立）：明牌、免費教學、不收費。

弱詞降權的理由：「免費教學」「不收費」在補習、餐飲、健身、公益貼文裡是中性詞；「明牌」單獨出現時多半指樂透或廟口明牌，辨識力遠低於「報明牌」。另外，否定語境照樣算證據——「不報明牌、不收費、不代操」正是這類貼文的標準開場白。

被其他命中詞包含的短詞會去重（「明牌」被「報明牌」包含時只留長詞），避免同一段文字被重複計數。

### 2.4 負向邊界

「賴」在中文裡是姓氏也是常用動詞，誤殺成本遠高於漏抓，因此提及本身就要排除下列語境：**信賴、依賴、無賴、仰賴、倚賴**——「我信賴：這個品牌」後面的冒號是正常標點，不是 LINE 帳號引導，而這種句子很可能同時帶投資詞，光靠話術詞的二次確認擋不住。「賴」「籟」單獨出現（賴清德、賴床、籟聲）一律不算提及，配上群組詞也不命中。

排除清單刻意只列這五個字。真實招攬句（例如「我的賴：某帳號」）前面同樣是中文，把規則擴成「前面是中文就不算」會整組漏抓。片語型限定「加入／加我」也是同一個考量——只認「加賴」會把「加賴床」一起收進來；「加 LINE」不受此限，因為 LINE 是專名，沒有那種歧義。

`LINE` 是英文詞的常見片段，單字型與帳號型都要求前面不接英文字母、單字型連後面也不接：**ONLINE、deadline、LINEUP、headline** 都不算提及。加入詞表刻意不收「加 LINE／加LINE」——片語型提及的區間本來就蓋住它，留著只會從 `加LINEUP`、`加LINEAR` 這類英文詞洩漏出來（片語型有後綴的負向邊界，純字串比對的詞表沒有）。

連結型網域的前面不得黏著英數、點、`@` 或斜線：**xxline.me/ti/g/x**、**9lin.ee/x**、**a.linktr.ee/x** 都是別人的網域，不是 LINE 的深連結。

### 2.5 正規化

比對前先把全形英數與全形標點（U+FF01–FF5E）平移成半形，再跑正則：招攬帳號會用全形英數規避純 ASCII 的帳號樣式。群組詞與加入詞的比對另外把 ASCII 小寫平移成大寫（「加line」也算加入詞）。兩種平移都只用於比對——換算後字串等長且逐位對齊，因此正則取得的位置可以直接套回原文切片，**證據片段保留使用者實際看到的全形字元**，好讓人一眼看出對方用了規避字元。控制字元與 bidi 字元在掃描前一併剝除（片段會寫進 storage 也會進選項頁 DOM）。

### 2.6 判定結果

偵測回傳 `{ hit, anchorMatch, pitchMatches, snippet, signals }`。`pitchMatches` 與 `hit` 分離：未命中時照樣回報有哪些話術詞，方便除錯與日後調參；`signals` 列出這次踩到的訊號類別（`link`／`line`／`group`／`join`／`pitch`），回溯判定走的是哪一條路。`anchorMatch` 與 `snippet` 只在命中時有意義。

提及取用優先序為連結 > 帳號 > 片語 > 單字，多種形式並存時挑帶帳號本體的那一個當 `anchorMatch` 與證據片段的中心，證據卡才看得到對方的 LINE 帳號。片段取提及起點前後各 40 字（提及本體算在後半，窗格不隨其長度延伸，否則帳號後面緊接的長串英數會被整段拖進片段），儲存上限同為 120 字。

## 3. 資料來源

| 用途 | 來源 | 網路請求 |
|---|---|---|
| 作者數字 id、帳號、顯示名稱、串文長度 | 詳情頁**伺服器預載資料**（頁面內 `script[type="application/json"]`，以網址列的貼文代碼比對，避免拿到同頁推薦的其他貼文） | 零 |
| 串文各篇文字 | 頁面 DOM 的貼文容器，以**作者帳號過濾**（他人回覆也是同一種容器，不算進串文） | 零 |
| 作者數字 id（備援） | 作者 id 在預載資料缺席時，對**該貼文的永久連結**做一次匿名請求，從回應取作者數字 id | 每篇貼文 24 小時最多一次 |

DOM 取值只認**使用者看得到的貼文容器**：由河道以 SPA 進入詳情頁時，Threads 不拆掉河道那一層 DOM，而是把它留在文件裡（祖先帶 `hidden` 屬性與行內 `display:none`），同一則貼文因而有兩張貼文代碼相同的卡片，看不見的舊卡文件序還在可見主文卡之前。串文取值、標記補回與標記名單查表三條路都會跳過隱藏子樹內的容器，判定文字與標記只落在可見的那一張。

比對用的主鍵是**數字 id** 而非帳號：對方改名換帳號仍然認得出是同一個人。標記名單另存一張「帳號 → id」的反查表，河道上只有帳號可用時靠它查表。

備援請求的約束：

- `credentials: 'omit'`，**不帶登入憑證**、不帶 cookie，也不帶可辨識使用者的資訊；請求對象就是使用者當下正在看的那一篇貼文本身。
- 回應必須先自證**文件身分**才採信該 id（交叉驗證），避免拿錯人：回應裡 `og:url`／`al:android:url` 的永久連結正規化後必須等於請求的那一篇（帳號不分大小寫），確認「拿回來的這份 HTML 就是我要的那一篇」，且回應內的作者 id 候選必須全部同值。身分標籤指向另一篇時一律不採信，這道否決優先於下一項。
- 回應沒有任何可正規化的身分標籤時（登入態或舊形狀的回應），退回舊判準：作者 id 前後各 2000 字內要找得到相符的**帳號名稱**。登出態的回應整份不帶帳號名稱，只有文件身分認得出那一篇。
- 非 2xx 回應一律不採信——錯誤頁的內容不是貼文本身，不得拿來背書任何 id。
- 同一篇貼文 24 小時內只發一次，另有每分鐘的全域上限；節流表本身也有筆數上限與過期淘汰。
- 總開關關閉時**一律不發**。
- 請求以 `AbortSignal.timeout()` 設逾時，不讓挂住的連線一直佔著節流名額；這支 API 自 Chrome 103 起才有，manifest 的 `minimum_chrome_version: "103"` 就是由它而來。
- 取不到 id（請求失敗、交叉驗證不過、逾時）時，頁面上仍掛標記，但**不寫入標記名單**——沒有穩定主鍵的條目會破壞名單語意。

處理輸入時的防呆上限：備援請求的回應只掃前 1 MB（登出態的回應實測約 581 KB，作者 id 落在文件中後段，上限太低會把它整段切在範圍外；仍保留天花板，不對超大回應做無界正則掃描），預載資料的走訪有深度與節點上限——頁面餵進來的是任意 JSON，沒有上限時畸形或刻意加深的結構會把主執行緒卡住。

## 4. 儲存形狀與上限

`chrome.storage.local.scamBlocklist`：

```js
{
  version: 1,
  entries: {
    [userId]: {
      handle,        // 原樣帳號（不帶 @）
      displayName,
      evidence: [{ postUrl, snippet, at }],
      addedAt,
      source,        // 'auto'（掃描命中）；'manual' 為保留值，v1 不產出
    },
  },
  handleIndex: {},   // handle 小寫 → userId 的反查表，一律由 entries 重建
  allowlist: {       // 使用者手動解除過的作者，不再自動加回
    [userId]: { at, handle },
  },
}
```

另有 `chrome.storage.local.scamGuardEnabled`（總開關，缺席視為開啟）。

備援請求的節流狀態另存兩把鍵，**一律寫 `chrome.storage.session`（環境沒有 session 空間時退回 `local`），瀏覽器關閉即清**：

| 鍵 | 內容 | 上限 |
|---|---|---|
| `scamAuthorFetchAt` | 以貼文網址為鍵的最近請求時間，撐起「同一篇貼文 24 小時只發一次」 | 500 筆，超過或滿 24 小時即淘汰 |
| `scamAuthorFetchLog` | 近一分鐘內發出的請求時戳，撐起每分鐘的全域上限 | 只留一分鐘內的時戳 |

這兩把鍵是節流狀態，不是使用者資料：只記「這個網址剛問過」與「剛才問了幾次」，同樣不上傳、不隨雲端同步。

| 上限 | 值 | 說明 |
|---|---|---|
| 名單筆數 | 5,000 位作者 | 依加入時間降冪保留，最舊的先淘汰 |
| 每位作者的證據 | 3 筆 | 依時間降冪保留最新的；同一篇貼文不重複記 |
| 證據片段 | 120 字 | 儲存與顯示同一道天花板 |
| 整包軟預算 | 2 MB | 以序列化後的 UTF-8 **位元組**計，超出即續裁最舊的條目。分母是 `chrome.storage.local` 的配額：Chrome 114 起為 10 MB，2 MB 約佔兩成；更早的版本為 5 MB，此時約佔四成。manifest 的下限 Chrome 103 落在 5 MB 配額的那幾版，四成仍在安全水位。證據放滿時實際可容約 1,500–2,500 位作者，筆數上限先到或預算先到都會觸發淘汰 |
| 白名單筆數 | 5,000 位作者 | 同樣依時間淘汰 |

正規化規則：從 storage 讀回時一律重算成上述四欄形狀，未知欄位不保留；`handleIndex` 永遠由 `entries` 重建，不信任存下來的反查表（否則會留下指向已刪條目的孤兒鍵）；原型污染用的鍵一律拒收；`entries` 與 `allowlist` 的鍵必須是 userId 形狀（純數字字串、1–20 位），不符的整筆剝除——鍵不驗形狀時，任意字串都能混成一筆永遠對不上寫入側 userId 的幽靈條目。

寫入權集中在 background：只有 background 寫 `scamBlocklist`，content script 與選項頁一律直接讀 storage 並監聽變更事件，避免多處併寫互相覆蓋。

## 5. 介面行為

- **貼文詳情頁**：命中時在主文互動列上方掛一枚標記（文案 `scamTagLabel`：「LINE 群組引導」，滑鼠提示 `scamTagTooltip`：「這串貼文含引導加入 LINE 或群組的字句，常見於投資招攬。請自行判斷，勿輕易加好友或提供個資。」），使用警告色而非錯誤色。
- **首次提示**：該次瀏覽階段第一次成功加入標記名單時跳一次 toast（`scamFirstHitToast`），告知已加入本機標記名單、可在設定頁管理；之後不再重複打擾。
- **河道**：只標記已在標記名單裡的作者，靠帳號反查表比對，不做全文掃描。
- **選項頁標記名單卡**（設定卡之後、紀錄卡之前）：
  - 每一列顯示顯示名稱 · @帳號、加入時間，以及「證據」小節——每筆證據一條連到該貼文的連結（新分頁開啟），連結文字取證據片段前段。沒有顯示名稱時第一行只顯示帳號，不重複。
  - 「解除」按鈕採 circle-minus 圖示（與刪除紀錄的垃圾桶區隔），二次確認後把該作者移出名單並寫進白名單。
  - 「已解除」小節列出白名單，可「復原」把作者移回可被偵測的狀態。
  - 空狀態顯示「目前沒有被標記的作者」，計數為零時顯示「0 位作者」。
- **設定卡**：總開關「LINE 群組引導標記」，說明文案直說「名單只存在這台裝置，不上雲」。

介面文案中英雙語，跟隨既有的介面語言設定。

## 6. 訊息協議

content script 與選項頁都不直接寫名單，一律送訊息給 background。

| 訊息 | 方向 | 內容 | 回應 |
|---|---|---|---|
| `scam.hit` | content script → background | `{ userId｜null, handle, displayName, postUrl, snippet, anchorMatch, pitchMatches, at }` | `{ ok: true, added, entry }`；作者已在白名單時回 `{ ok: true, added: false, allowlisted: true }` |
| `scam.blocklist.remove` | 選項頁 → background | `{ userId }` | `{ ok: true }`，同時寫進白名單並重建反查表 |
| `scam.blocklist.restore` | 選項頁 → background | `{ userId }` | `{ ok: true }`，把作者移出白名單 |

失敗一律回 `{ ok: false, code }`：

| 回應碼 | 情境 |
|---|---|
| `bad_request` | 欄位形狀不合（帳號或貼文網址格式不對、片段超長、id 不是純數字字串、時間不是數字） |
| `no_user_id` | 預載資料沒有作者 id，備援也取不到——頁面照樣掛標記，但不入名單 |
| `disabled` | 總開關關閉，不寫入也不發請求 |
| `internal_error` | 讀寫本機儲存失敗 |

`anchorMatch` 與 `pitchMatches` 隨訊息送出是為了讓判定依據與命中同時可見（除錯、日後調參），但 background **目前不取用、也不落盤**——寫進證據的只有 `postUrl`、`snippet`、`at` 三欄。

訊息來源會驗證：`scam.hit` 只接受來自 Threads 分頁的 content script，名單管理訊息只接受來自本擴充功能頁面。

## 7. 誤報處置

誤判由使用者一鍵推翻，而且**推翻就是終局**：

1. 在選項頁標記名單卡按「解除」，二次確認。
2. 該作者移出名單，同時寫進白名單。
3. 之後再次掃到同一位作者的貼文，**不會自動加回**——偵測仍會判定，但寫入端在白名單上直接短路，回報「已在白名單」。
4. 若使用者反悔，可在「已解除」小節按「復原」，把作者移出白名單、恢復成可被自動加入的狀態。

設計取向：誤殺成本高於漏抓。被誤標的是一個真人帳號，標錯會讓使用者不信任整個功能；漏抓只是回到沒有這個功能的狀態。所有調參（雙訊號門檻、群組／加入詞的獨立性要求、弱詞降權、負向邊界）都往同一個方向倒。

## 8. 已知限制

- **河道只標已知作者**：時間軸上不做全文判定，因此第一次遇到的招攬帳號要等使用者點進詳情頁才會被認出來。
- **只判自回覆串**：判定對象是作者自己的串文；引導文字若出現在他人回覆、圖片、影片或外部聚合頁內文，本版偵測不到。
- **規則是中文取向**：提及樣式與群組／加入／話術詞表針對繁體中文的招攬語境，其他語言的同類劇本不在本版範圍。
- **規則隨版本內建**：`SCAM_RULES` 這一版直接寫在前端程式碼裡，改詞表要跟著發版；由後端下發規則包是後續的事。
- **v1 不支援手動加入**：沒有數字 id 的條目會破壞名單主鍵的語意，因此不提供手動輸入帳號加入標記名單，延後評估。
- **不共享、不同步**：名單只存在這台裝置。換一台瀏覽器要重新累積，也沒有任何跨使用者的共享名單——這是刻意的取捨，社群回報名單牽涉審核責任與濫用風險。
- **Threads 改版風險**：偵測依賴詳情頁的伺服器預載資料結構與頁面 DOM 結構，兩者都可能隨 Threads 改版而變動。降級行為是**靜默退場**：取不到預載資料就只靠 DOM 文字，取不到作者 id 就只掛標記不入名單，兩者都取不到就什麼都不做——絕不在資料不全時猜測歸屬，也不影響插件既有的連結淨化功能。
- **轉發卡跟著內容作者走**：河道上的轉發卡片以被轉發貼文的作者為準——中立帳號轉發被標記作者的貼文會被標記，被標記的作者轉發他人貼文則不會。判準是卡片上的貼文連結指向誰，不是誰按了轉發。
- **證據連結會失效**：證據指向原貼文的永久連結，貼文若被刪除或帳號被停用，連結會連不到內容；名單上的條目與片段仍保留在本機。
